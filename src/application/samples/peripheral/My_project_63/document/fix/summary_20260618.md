## 四、⚠️ 需要原负责人处理的问题

### 1. @in,confirm 不 BIND（高优先级）

当前入库 confirm 不绑定 BS21E。后果：
- BS21E 内部 tag_id 保持为 0（默认值），广播中 tag_id=0
- 依赖 WS63 端 `scan_table_add_or_update` 的 **MAC 优先匹配**（FIX-02）来识别已注册标签
- 断电重启后 BS21E 仍广播 tag_id=0，WS63 从 NV 恢复 biz_map 后通过 MAC 匹配恢复 tag_id

**需要做的**：调试 SLE 连接→配对→SSAP→BIND_TAG 全链路稳定性。建议做成**非阻塞后台操作**：标签在范围内时自动连接绑定，不阻塞主流程。

相关代码路径：
- `biz_screen_in_confirm()` — 当前不连
- `biz_check_confirm_bind()` — 检查 SSAP 就绪后发 BIND_TAG（已无用）
- `sle_network_connect_by_tag()` → SSAP → `sle_network_send_cmd(BIND_TAG)`

### 2. SLE 扫描表/连接稳定性

- 出库时 `@out,start` 扫描偶尔扫不到标签（多次点击才命中）
- 入库扫描逻辑不稳定
- `sle_stop_seek` 异步，`my63_seek_disable_cb` 回调时序不确定，可能导致连接冲突

### 3. 寻物蜂鸣器未触发

- `@find,locate` → `sle_network_connect_by_tag` → `SSAP_CMD_FIND` → 直接返回"未找到"
- 怀疑 SLE 连接或 SSAP FIND 命令参数不对

### 4. 全局盘点已测试通过 ✅

### 5. SSAP BIND_TAG 成功后需处理的事项

BIND_TAG 成功后 `biz_sle_notify_cb` 回调中：
- 更新 `entry->status = BIZ_TAG_BOUND`
- 发送蜂鸣 `SSAP_CMD_FIND`（5s 后自动停止）
- MQTT 上云

当前这些逻辑已存在于 `biz_sle.c`，只等 BIND 成功后触发。
