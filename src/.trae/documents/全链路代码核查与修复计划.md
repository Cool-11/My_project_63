## 一、静态代码分析

### 🔴 BUG-01：UART引脚配置错误 → 串口命令无法到达代码
- **文件**：`uart_vision.h` 第10-13行
- **当前值**：`UV_UART_BUS=1, TX_PIN=15, RX_PIN=16`
- **正确值**：`UV_UART_BUS=0, TX_PIN=41(S_AGPIO9), RX_PIN=42(S_AGPIO10)`
- **根因**：烧录口是UART0(GPIO41/42)，代码监听UART1(GPIO15/16)，AT框架又占用了UART0
- **影响**：串口助手发的数据被AT框架拦截，`uv_uart_rx_cb` 从未被调用

### 🔴 BUG-02：环形缓冲区 `uv_ring_has_newline()` 只检测 `\n`，不检测 `\r`
- **文件**：`uart_vision.c` 第37行
- **代码**：`if (g_uv_ring[i] == '\n' && dist < UV_LINE_MAX)`
- **问题**：串口助手按Enter发送 `\r\n`，`\r` 不被识别为行结束符
- **注意**：`uv_ring_read_line()` 第56行已经跳过 `\r`，但 `has_newline()` 不认 `\r`，导致数据卡在缓冲区
- **修复**：第37行改为 `if ((g_uv_ring[i] == '\n' || g_uv_ring[i] == '\r') && dist < UV_LINE_MAX)`

### 🔴 BUG-03：`uart_vision_send_json()` 越界写入 → 可能随机崩溃
- **文件**：`uart_vision.c` 第221-223行
- **代码**：
  ```c
  char *out = cJSON_PrintUnformatted(root);  // 分配 strlen+1 字节
  uint32_t out_len = (uint32_t)strlen(out);
  out[out_len] = '\n';   // ← 越界！cJSON分配的空间没有+1给\n
  out_len++;
  ```
- **问题**：`cJSON_PrintUnformatted` 返回的缓冲区大小是 `strlen(out)+1`（含`\0`），在 `out[out_len]` 位置写 `\n` 会覆盖 `\0` 后面的内存
- **影响**：堆内存破坏，可能导致随机崩溃或数据损坏
- **修复**：分两次写，先写JSON再写 `\n`

### 🟡 BUG-04：`uv_uart_rx_cb` 无调试日志
- **文件**：`uart_vision.c` 第73-79行
- **问题**：回调中无日志，无法确认回调是否被触发
- **修复**：添加 `osal_printk("[WS63_UART] rx_cb len=%u\r\n", length);`

### 🟡 BUG-05：SLE已连接+已认证但 `ssap_ready=0` → SSAP交换未触发
- **文件**：`sle_network.c` 第478-503行
- **日志证据**：`connected=1, authenticated=1, ssap_ready=0`
- **分析**：
  - `my63_connect_state_changed_cb` 中，连接成功后检查 `pair_state`
  - 如果 `pair_state == SLE_PAIR_NONE`，调用 `sle_pair_remote_device()`
  - 配对成功后 `my63_pair_complete_cb` 调用 `my63_start_ssap_exchange()`
  - 但如果 `pair_state != SLE_PAIR_NONE`（已配对），直接 `authenticated=1` 并调用 `my63_start_ssap_exchange()`
- **可能原因**：
  1. `my63_start_ssap_exchange()` 调用了 `ssapc_exchange_info_req()` 但回调 `my63_ssap_exchange_info_cb` 中 `status != ERRCODE_SLE_SUCCESS`
  2. SSAP发现服务UUID不匹配（BS21E端GATT Service UUID与WS63端 `0xFF00` 不一致）
  3. **魔数大小端问题**：BS21E广播中manufacturer data的magic `0xAABBCCDD` 如果是大端序存储，WS63端 `read_le32` 读出来就是 `0xDDCCBBAA`，导致 `shared_protocol_validate` 失败 → `my63_extract_adv_field` 返回0 → 只能靠 `local_name` 匹配 → 连接后SSAP交换失败
- **修复方向**：需要BS21E端确认GATT Service UUID和广播数据格式

### 🟡 BUG-06：`biz_cmd_mqtt_connect` 中3处 `strncpy_s` 未检查返回值
- **文件**：`business_logic.c` 第505/510/515行
- **代码**：
  ```c
  strncpy_s(params.client_id, ...);   // ← 返回值未检查
  strncpy_s(params.username, ...);    // ← 返回值未检查
  strncpy_s(params.password, ...);    // ← 返回值未检查
  ```
- **影响**：截断时无错误提示，params中可能包含不完整数据

### 🟢 BUG-07：NV存储首次读取失败（正常行为）
- `0x80003081 = ERRCODE_NV_KEY_NOT_FOUND`
- 首次上电Key不存在是正常的，不影响功能

## 五、修复步骤（按优先级）

### Step 1：修复 uart_vision.h（UART0引脚）
- `UV_UART_BUS` → 0
- `UV_UART_TX_PIN` → 41
- `UV_UART_RX_PIN` → 42

### Step 2：修复 uart_vision.c（4处问题）
- 2a: `uv_ring_has_newline()` 增加 `\r` 检测
- 2b: `uv_uart_rx_cb()` 增加调试日志
- 2c: `uart_vision_send_json()` 修复越界写入（分两次write）
- 2d: 增加超时处理（100ms无新数据当作完整行）

### Step 3：修复 business_logic.c（strncpy_s返回值）
- 3处 `strncpy_s` 增加返回值检查

### Step 4：修改 menuconfig（AT框架迁移到UART2）
- `CONFIG_AT_UART=2`
- 需要全量烧录

### Step 5：SLE SSAP问题排查
- 需要BS21E端确认：
  1. GATT Service UUID是否为 `0xFF00`
  2. GATT Property UUID是否为 `0xFF01`
  3. 广播中manufacturer data的magic字节序（大端or小端）
  4. 广播中local_name是否为 `"BS2x_Tag"`
